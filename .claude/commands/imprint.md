ইউআই-এর ধারাবাহিকতা (UI consistency) এমনি এমনি আসে না। এটি তখনই ঘটে যখন প্রতিটি কম্পোনেন্ট তৈরি করার সময় আগে থেকে কী কী বিদ্যমান আছে সে সম্পর্কে ধারণা থাকে।

এআই (AI) দ্বারা তৈরি ইন্টারফেসের সমস্যা হলো, প্রতিটি কম্পোনেন্ট আলাদাভাবে বা আইসোলেশনে তৈরি হয়। এজেন্ট মনে রাখে না যে সে তিনটি সেশন আগে কী তৈরি করেছিল। ফলে স্পেসিং বা ফাঁকা জায়গা এদিক-ওদিক হয়ে যায়। কালার বা রঙে সামান্য তারতম্য ঘটে। বর্ডার রেডিয়াসে অমিল দেখা দেয়। অ্যাপটি দেখে মনে হয় এটি ভিন্ন ভিন্ন রুচির একাধিক মানুষ মিলে তৈরি করেছে।

এই স্কিল বা দক্ষতা সেই সমস্যার সমাধান করে। যেকোনো ইউআই কম্পোনেন্ট তৈরি করার পর এটি রান করুন। এটি সদ্য তৈরি হওয়া কোডটি পড়বে, ধারাবাহিকতার জন্য প্রয়োজনীয় প্যাটার্নগুলো এক্সট্রাক্ট করবে এবং সেগুলো সংরক্ষণ করবে যাতে ভবিষ্যতের প্রতিটি কম্পোনেন্ট এটার সাথে ম্যাচ করতে পারে।

একটি মাত্র কমান্ড। প্রতিবার এটি রান করুন। পুরো সিস্টেমটি মূলত এটাই।

## যেভাবে ইনভোক বা রান করবেন (How to Invoke)

যেকোনো ইউআই কম্পোনেন্ট তৈরি করার পর রান করুন:

```

/imprint

```

নির্দিষ্ট কোনো ফাইলকে টার্গেট করতে রান করুন:

```

/imprint [filepath]

```

বিদ্যমান কোডবেসে কোনো অমিল বা অসঙ্গতি আছে কিনা তা অডিট করতে রান করুন:

```

/imprint audit

```

যদি কোনো ফাইলের পাথ (filepath) দেওয়া না হয়, তবে এই স্কিলটি স্বয়ংক্রিয়ভাবে এই সেশনে সম্প্রতি তৈরি বা পরিবর্তন করা কম্পোনেন্ট ফাইলগুলো শনাক্ত করবে এবং সেখান থেকে প্যাটার্ন সংগ্রহ করবে।

**কখন অডিট (audit) মোড ব্যবহার করবেন:**

- প্রজেক্টের ইউআই ইতিমধ্যে তৈরি আছে কিন্তু সেটির ধারাবাহিকতা বা কনসিস্টেন্সি নিয়ে সন্দেহ আছে
- `/imprint` রান না করেই একাধিক সেশন পার হয়ে গেছে
- কোনো কিছু দেখতে ভিজ্যুয়ালি অদ্ভুত লাগছে কিন্তু ঠিক কী কারণে এমন লাগছে তা সুনির্দিষ্ট করা যাচ্ছে না
- কোনো বিদ্যমান প্রজেক্টে প্রথমবার `ui-registry.md` তৈরি করার আগে

এমন যেকোনো প্রজেক্ট যেখানে শুরু থেকেই ইউআই ট্র্যাক করা হয়নি, সেখানে যেকোনো কম্পোনেন্টের ওপর `/imprint` রান করার আগে `/imprint audit` রান করুন।

## ধাপ ১ — মাত্র কী তৈরি করা হয়েছে তা খুঁজে বের করুন

যদি কোনো ফাইলের পাথ (filepath) দেওয়া থাকে — তবে সরাসরি সেই ফাইলটি পড়ুন।

যদি কোনো ফাইলের পাথ দেওয়া না থাকে — তবে এই সেশনে কোন কম্পোনেন্ট ফাইলগুলো সবচেয়ে সম্প্রতি তৈরি বা পরিবর্তন করা হয়েছে তা শনাক্ত করুন। কম্পোনেন্টস ডিরেক্টরি (components directory) এবং অন্য যেসব জায়গায় ইউআই ফাইল সাধারণত থাকে, সেখানে খুঁজুন। সেই ফাইলগুলো পড়ুন।

কোন ফাইলগুলো থেকে প্যাটার্ন সংগ্রহ করতে হবে তা যদি অস্পষ্ট হয়, তবে ডেভেলপারকে জিজ্ঞাসা করুন:

```

Which component should I capture patterns from?

```

## ধাপ ২ — ধারাবাহিকতার জন্য যা গুরুত্বপূর্ণ তা এক্সট্রাক্ট করুন

কম্পোনেন্টের কোডটি পড়ুন। পুরো ইন্টারফেসে ভিজ্যুয়াল ধারাবাহিকতা বজায় রাখতে প্রভাব ফেলে এমন ক্লাস এবং ভ্যালুগুলোই কেবল এক্সট্রাক্ট বা সংগ্রহ করুন। সবকিছু নয় — কেবল সেই বিষয়গুলোই নিন যা দেখলে মনে হয় কম্পোনেন্টগুলো একই পরিবারের অংশ।

**এগুলো এক্সট্রাক্ট করুন:**

- ব্যাকগ্রাউন্ড (Background) — কন্টেইনার, কার্ড বা প্যানেলের জন্য কোন bg- ক্লাস ব্যবহার করা হয়েছে
- বর্ডার (Border) — বর্ডারের রঙ, বর্ডারের প্রস্থ (width) এবং বর্ডারের স্টাইল
- বর্ডার রেডিয়াস (Border radius) — এই ধরনের কম্পোনেন্টের জন্য কোন rounded- ক্লাস ব্যবহার করা হয়েছে
- টেক্সট কালার (Text colors) — প্রাইমারি টেক্সট, সেকেন্ডারি টেক্সট এবং মিউটেড টেক্সটের ক্লাসসমূহ
- টেক্সটের সাইজ ও ওয়েট (Text sizes and weights) — হেডিং, বডি, লেবেল এবং ক্যাপশনের জন্য ব্যবহৃত ক্লাস
- স্পেসিং (Spacing) — কম্পোনেন্টের ভেতরের প্যাডিং এবং উপাদানগুলোর মধ্যকার গ্যাপ (gap)
- ইন্টারেক্টিভ স্টেট (Interactive states) — হোভার (hover), ফোকাস (focus) এবং অ্যাক্টিভ (active) ক্লাসসমূহ
- শ্যাডো (Shadow) — যদি ব্যবহার করা হয়ে থাকে
- যেকোনো এক্সেন্ট (accent) বা ব্র্যান্ড কালারের ব্যবহার

**এগুলো এক্সট্রাক্ট করবেন না:**

- উইডথ এবং হাইট (Width and height) — এটি কনটেক্সটের ওপর খুব বেশি নির্ভরশীল, তাই এটিকে ধারাবাহিকতার নিয়ম বানানো যাবে না
- ফ্লেক্স এবং গ্রিড লেআউট (Flex and grid layout) — এটি স্ট্রাকচারাল বা কাঠামোগত বিষয়, ভিজ্যুয়াল নয়
- পজিশনিং (Positioning) — absolute, relative, z-index — এগুলো কনটেক্সটের ওপর নির্ভরশীল
- অ্যানিমেশন এবং ট্রানজিশন টাইমিং — যদি না এটি এমন কোনো প্যাটার্ন হয় যা সব জায়গায় বজায় রাখা জরুরি
- রেসপনসিভ ব্রেকপয়েন্ট ভ্যারিয়েন্ট — কেবল মূল বা বেস (base) প্যাটার্নটি সংগ্রহ করুন

## ধাপ ৩ — ui-registry.md ফাইলে লিখুন

`ui-registry.md` ফাইলটি ওপেন করুন। যদি এটি না থাকে, তবে তৈরি করুন।

যে কম্পোনেন্টটি ক্যাপচার করা হয়েছে সেটির জন্য একটি নতুন এন্ট্রি বা তথ্য যুক্ত করুন। বিদ্যমান এন্ট্রিগুলো ওভাররাইট (overwrite) করবেন না — রেজিস্ট্রির শেষে নতুনটি অ্যাপেন্ড বা যুক্ত করুন।

যদি এই ধরনের কম্পোনেন্টের জন্য ইতিমধ্যে কোনো এন্ট্রি থেকে থাকে — তবে ডুপ্লিকেট না করে সেটি আপডেট করুন।

### এন্ট্রি ফরম্যাট (Entry format)

```markdown
### [Component Name]

File: [filepath]
Last updated: [date]

| Property         | Class           |
| ---------------- | --------------- |
| Background       | [class]         |
| Border           | [class]         |
| Border radius    | [class]         |
| Text — primary   | [class]         |
| Text — secondary | [class]         |
| Spacing          | [class]         |
| Hover state      | [class]         |
| Shadow           | [class or none] |
| Accent usage     | [class or none] |

**Pattern notes:**
[প্যাটার্ন সংক্রান্ত যেকোনো গুরুত্বপূর্ণ সিদ্ধান্ত যা নোটে রাখা প্রয়োজন —
কেন একটি নির্দিষ্ট ক্লাস বেছে নেওয়া হলো, এই কম্পোনেন্টটি সবসময়
কিসের সাথে মিলতে হবে, কোন কোন ভ্যারিয়েশনের অনুমতি আছে]
```

## ধাপ ৪ — কী ক্যাপচার করা হয়েছে তা নিশ্চিত করুন

ui-registry.md ফাইলে লেখার পর, ডেভেলপারকে কনফার্ম বা নিশ্চিত করুন:

```
Imprinted [Component Name] → ui-registry.md

Captured:
- Background: [class]
- Border: [class]
- Radius: [class]
- Text: [classes]
- Spacing: [classes]
- Hover: [class]

Any future component of this type should match these patterns.

```

যদি এক্সট্রাক্ট করার সময় কোনো কিছু অসঙ্গতিপূর্ণ বা আশ্চর্যজনক মনে হয় — তবে সেটি ফ্ল্যাগ (flag) বা চিহ্নিত করুন:

```
Note: [এমন কিছু যা অসঙ্গতিপূর্ণ মনে হয়েছে বা যা ডেভেলপারের জানা উচিত বলে আপনি মনে করেন]

```

## যেভাবে ui-registry.md ব্যবহৃত হয়

এই রেজিস্ট্রিটি কেবল একটি রেকর্ড বা খাতা নয়। এটি ভবিষ্যতের প্রতিটি সেশনের জন্য ধারাবাহিকতা নিশ্চিত করার হাতিয়ার।

ইউআই সংক্রান্ত কাজ রয়েছে এমন যেকোনো সেশনের শুরুতে, কোনো কম্পোনেন্ট লেখার আগেই ক্লড (Claude) `ui-registry.md` ফাইলটি পড়ে নেয়। যখন একটি নতুন কার্ড তৈরি করা হয়, তখন এটি দেখে নেয় বিদ্যমান কার্ডগুলো কীভাবে তৈরি করা হয়েছিল। যখন একটি নতুন বাটন তৈরি করা হয়, তখন এটি দেখে বাটনের কোন প্যাটার্নগুলো ইতিমধ্যে রয়েছে। যখন একটি নতুন স্ট্যাটাস ব্যাজ তৈরি করা হয়, তখন এটি ইতিমধ্যে ব্যবহৃত হুবহু সেই ক্লাসগুলোর সাথে মিল রেখে তৈরি করে।

প্রজেক্ট যত বড় হয়, এই রেজিস্ট্রিও তত সমৃদ্ধ হয়। যত বেশি কম্পোনেন্ট ইমপ্রিন্ট করা হবে, প্রতিটি নতুন কম্পোনেন্ট তত বেশি ধারাবাহিক হবে — কারণ ক্লডের কাছে ইতিমধ্যে কী আছে তার একটি নিখুঁত রেফারেন্স সবসময় থাকে।

## মূল নিয়ম (The Rule)

একটি কম্পোনেন্ট তৈরি করুন। `/imprint` রান করুন। পরের কাজে এগিয়ে যান।

প্রতিবার। কোনো ব্যতিক্রম ছাড়াই।

দশটি এন্ট্রি সমৃদ্ধ একটি রেজিস্ট্রি দরকারী। ত্রিশটি এন্ট্রি সমৃদ্ধ একটি রেজিস্ট্রি শক্তিশালী। আর যে রেজিস্ট্রি মাঝে মাঝে আপডেট করা হয়, সেটি নির্ভরযোগ্য নয়।

ধারাবাহিকতা বা কনসিস্টেন্সি একটি অভ্যাস, কোনো ফিচার নয়।

## অডিট মোড — /imprint audit

এটি তখন রান করুন যখন ইউআই ইতিমধ্যে বিদ্যমান এবং সেটির ধারাবাহিকতা নিয়ে নিশ্চিত হওয়া যাচ্ছে না। একটি মাত্র কম্পোনেন্ট থেকে প্যাটার্ন নেওয়ার পরিবর্তে, এটি পুরো কোডবেস স্ক্যান করে, দ্বন্দ বা অমিলগুলো খুঁজে বের করে এবং পরবর্তীতে যেকোনো প্যাটার্ন ক্যাপচার করার আগে একটি পরিষ্কার বেসলাইন বা ভিত্তি তৈরি করে।

### স্টেজ ১ — সমস্ত ইউআই কম্পোনেন্ট স্ক্যান করুন

প্রজেক্টের প্রতিটি কম্পোনেন্ট ফাইল খুঁজে বের করুন। প্রতিটি ফাইল পড়ুন। পুরো ইন্টারফেসে বর্তমানে কোন কোন ভিজ্যুয়াল প্যাটার্ন ব্যবহার করা হচ্ছে তার একটি সম্পূর্ণ চিত্র তৈরি করুন।

### স্টেজ ২ — অমিল বা দ্বন্দ্বসমূহ (Conflicts) চিহ্নিত করুন

ধারাবাহিকতার জন্য গুরুত্বপূর্ণ প্রতিটি ভিজ্যুয়াল প্রোপার্টির জন্য, খুঁজে পাওয়া সমস্ত ভ্যারিয়েশন বা ভিন্নতা তালিকাভুক্ত করুন:

```
## UI Consistency Audit

### Conflicts found

**Border radius**
[খুঁজে পাওয়া প্রতিটি rounded- ভ্যারিয়েন্ট এবং কোন কোন কম্পোনেন্ট সেটি ব্যবহার করছে তার তালিকা]
Recommendation: [কোনটিকে স্ট্যান্ডার্ড বা আদর্শ হিসেবে ধরা উচিত এবং কেন]

**Background colors**
[খুঁজে পাওয়া প্রতিটি bg- ক্লাসের তালিকা — কোনো হার্ডকোডেড হেক্স ভ্যালু থাকলে তা ফ্ল্যাগ করুন]
Recommendation: [ডিজাইন সিস্টেমের কোন টোকেন ক্লাসগুলো দিয়ে এগুলো প্রতিস্থাপন করা উচিত]

**Text colors**
[খুঁজে পাওয়া প্রতিটি text- কালার ক্লাসের তালিকা — ডিজাইন সিস্টেমকে বাইপাস করে এমন কোনো ক্লাস থাকলে তা ফ্ল্যাগ করুন]
Recommendation: [কোন টোকেন ক্লাস দিয়ে এগুলো প্রতিস্থাপন করা উচিত]

**Spacing**
[প্যাডিং এবং গ্যাপের ক্ষেত্রে খুঁজে পাওয়া ভ্যারিয়েশনসমূহের তালিকা]
Recommendation: [কোন ভ্যালু বা মানগুলোকে স্ট্যান্ডার্ড হিসেবে নেওয়া উচিত]

**Border colors**
[খুঁজে পাওয়া প্রতিটি বর্ডার কালার ক্লাসের তালিকা]
Recommendation: [কোন টোকেন ক্লাসটিকে স্ট্যান্ডার্ড হিসেবে নেওয়া উচিত]

**Interactive states**
[হোভার, ফোকাস, অ্যাক্টিভ স্টেটের ক্ষেত্রে খুঁজে পাওয়া ভ্যারিয়েশনসমূহের তালিকা]
Recommendation: [কোন প্যাটার্নটিকে স্ট্যান্ডার্ড হিসেবে নেওয়া উচিত]

### Hardcoded values found
[খুঁজে পাওয়া প্রতিটি হার্ডকোডেড হেক্স ভ্যালু, র কালার ক্লাস বা নন-টোকেন ভ্যালুর তালিকা — ফাইল এবং লাইন নম্বর সহ]
এগুলোকে অবশ্যই ডিজাইন সিস্টেমের টোকেন দ্বারা প্রতিস্থাপন করতে হবে।

### Recommended baseline
[প্রতিটি প্রোপার্টির জন্য সঠিক প্যাটার্ন — যা মূলত কোডের অধিকাংশ জায়গায় ইতিমধ্যে সঠিকভাবে কী ব্যবহৃত হচ্ছে এবং ডিজাইন সিস্টেমে কী ডিফাইন করা আছে তার ওপর ভিত্তি করে নির্ধারিত]

```

### স্টেজ ৩ — ডেভেলপারের নিশ্চিতকরণের জন্য অপেক্ষা করুন

অডিট রিপোর্টটি উপস্থাপন করুন। কোনো কিছু নিজে থেকে ঠিক করতে যাবেন না। এখনই `ui-registry.md` আপডেট করবেন না।

ডেভেলপারকে জিজ্ঞাসা করুন:

```
Audit complete. [X] conflicts found across [Y] properties.

Before I establish the baseline in ui-registry.md:
1. Do the recommendations above look correct?
2. Are there any conflicts you want to resolve differently?
3. Should I flag the hardcoded values as issues to fix?

Confirm the baseline and I will write it to ui-registry.md.

```

### স্টেজ ৪ — নিশ্চিত হওয়া বেসলাইনটি লিখুন

ডেভেলপার নিশ্চিত করার পর — সম্মত হওয়া বেসলাইনটি ভিত্তি হিসেবে `ui-registry.md` ফাইলে লিখুন। এটি স্পষ্টভাবে লেবেল করুন:

```markdown
## Baseline — Established [date]

[Note: This baseline was established via /imprint audit]

| Property         | Correct class |
| ---------------- | ------------- |
| Card background  | [class]       |
| Card border      | [class]       |
| Card radius      | [class]       |
| Button primary   | [class]       |
| Button secondary | [class]       |
| Text primary     | [class]       |
| Text secondary   | [class]       |
| Text muted       | [class]       |
| Input background | [class]       |
| Input border     | [class]       |
```

### স্টেজ ৫ — যা যা ঠিক করা প্রয়োজন তার তালিকা তৈরি করুন

বেসলাইন লেখার পর, একটি ফিক্স লিস্ট (fix list) বা সংশোধনী তালিকা তৈরি করুন — অর্থাৎ যে সমস্ত কম্পোনেন্ট এই বেসলাইন থেকে বিচ্যুত হয়েছে বা অমিল রয়েছে:

```
## Components to fix

These components deviate from the confirmed baseline
and should be updated:

- [Component file] — [কী ভুল আছে] → [এটি কেমন হওয়া উচিত]
- [Component file] — [কী ভুল আছে] → [এটি কেমন হওয়া উচিত]

```

ডেভেলপার এখন এগুলো সুবিন্যস্তভাবে ঠিক করতে পারেন — অথবা কাজ করার সময় যখনই যে কম্পোনেন্টের মুখোমুখি হবেন তখন ঠিক করে নিতে পারেন। যেভাবেই হোক না কেন, বেসলাইনটি তৈরি হয়ে গেল এবং নতুন কম্পোনেন্টগুলোর ধারাবাহিকতা বজায় রাখতে এখন থেকে সামনে এগিয়ে যাওয়ার জন্য `/imprint` ব্যবহার করা যাবে।

